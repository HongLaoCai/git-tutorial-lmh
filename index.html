Phần A · Bước 2

Tạo token PAT

PAT (Personal Access Token) dùng để xác thực khi làm việc với Git qua HTTPS.

  • Tạo token PAT trên GitLab (Access Tokens).
  • Copy token một lần — cần giữ an toàn.

Lưu ý trong tutKhi đăng nhập Git trên web mà không dùng PAT, hệ thống vẫn yêu cầu xác thực trên web; token cũng sẽ được lưu lại trên máy.

# Ví dụ dạng token (GIẢ — không dùng token thật trên slide)

Phần A · SSH

Dùng SSH keys

Ngoài PAT, có thể dùng SSH keys để xác thực với GitLab.

1. Xem danh sách SSH key trên máy

ls -la ~/.ssh

2. Tạo SSH key mới

ssh-keygen -t ed25519 -C "your.email@example.com"

PassphraseLúc tạo key có thể có pass — cần nhớ pass.

3. Xem nội dung key (public)

cat ~/.ssh/id_ed25519.pub

Copy nội dung file .pub rồi dán vào GitLab → SSH Keys.

4. Khi bị hỏi pass nhiều lần (macOS)

ssh-add --apple-use-keychain ~/.ssh/id_ed25519

Phần A · Clone repo

Clone repo + gắn PAT vào remote

Theo tut: clone bằng HTTPS kèm username + PAT, rồi set remote để sau không phải nhập lại.

1. Clone repo (ví dụ study 2026)

git clone https://USERNAME:glpat-xxxxxxxx@gitlab.com/group/studybooks-2026

2. Set PAT vào remote để sau không phải nhập

git remote set-url origin https://USERNAME:glpat-xxxxxxxx@gitlab.com/group/studybooks-2026.git

3. Check lại

Sau khi set-url, kiểm tra remote. Màn hình sẽ hiển thị dạng:

origin  https://USERNAME:glpat-xxxxxxxxxx@gitlab.com/group/studybooks-2026.git (fetch)
origin  https://USERNAME:glpat-xxxxxxxxxx@gitlab.com/group/studybooks-2026.git (push)

Bảo mậtKhông đưa token thật lên slide, chat hay commit. Token trong remote URL nằm plaintext trong máy.

Phần B · Lệnh thường dùng

Bộ lệnh dùng hàng ngày

Học thuộc vòng lặp này trước khi làm tình huống nâng cao.

git pull
git fetch
git add .
git status
git commit -m "commit"
git push origin main

git branch -a
git branch

git checkout
  • git status — xem đang có thay đổi gì
  • git add . — đưa thay đổi vào staging
  • git commit -m "…" — lưu thành 1 commit
  • git push origin main — đẩy lên remote nhánh main
  • git branch / git branch -a — xem nhánh local / tất cả
  • git checkout — chuyển nhánh / file (dùng kèm tham số)

Phần B · Conflict

Xử lý conflict khi merge

Khi merge có nhiều conflict, muốn xem / chọn code theo từng phía.

Giữ nguyên code gốc của nhánh hiện tại

git checkout --ours .

Giữ nguyên code gốc của nhánh đích (theirs)

git checkout --theirs .

Sau đó xem / sửa từng file

git checkout tenfile.abc

Sửa xong, save lại, rồi:

git add tenfile.abc
git commit -m "fix-conflict-tenfile.abc"

Hoặc sửa tất cả rồi mới commit:

git add .
git commit -m "fix-conflict-new-branch"

Tình huống 2

Code xong quên tạo branch

Ví dụ

Đang ở main, đã code (hoặc đã commit), muốn tạo branch mới để làm MR.

a. Chưa commit

Tạo và chuyển sang branch mới, rồi tiếp tục code.

git checkout -b feature-moi
# Hoặc:
git switch -c feature-moi

NhớPhải add và commit. Nếu không, khi quay lại main vẫn thấy thay đổi trong changes.

b. Đã commit

Dùng reset để khôi phục, rồi tạo branch như mục a.

git reset HEAD~1

c. Đã push

Vẫn dùng git reset HEAD~1 nếu chưa được merge.

Tình huống 3

Pull không được vì có commit local

Ví dụ

Có 1 commit cần push, và 2 commit cần pull.

a. Nếu chưa commit

Stash lại rồi pull về, fix conflict rồi tiếp tục.

git stash
git pull
git stash pop

b. Nếu đã commit

Reset để lấy lại code, stash, pull, rồi stash pop.

git reset HEAD~1
git stash
git pull
git stash pop

Sau đó fix conflict nếu có và tiếp tục.

Tình huống 4

Muốn bỏ các changes

Ví dụ

Đang làm tính năng mới, càng làm càng sai — chỉ muốn reset vài file để làm lại.

a. Chưa commit

Chọn discard changes trên UI, hoặc lệnh:

git restore tenfile.abc

# hoặc
git checkout tenfile.abc

b. Đã commit

Dùng git reset HEAD~1 để lấy lại code, sau đó discard file đó.

Nếu có nhiều commit — xem danh sách:

git log --oneline

Chọn commit cần về (ví dụ 4b6bd5d):

git checkout 4b6bd5d -- tenfile.abc

Nếu về thẳng nội dung từ một branch (ví dụ main):

  • Cách thủ công: mở branch main, copy file, paste ngược vào.
  • Hoặc lệnh:
git checkout main -- tenfile.abc

Tình huống 5

Commit thiếu file

Ví dụ

Commit xong chưa push, nhớ ra chưa tăng version — muốn gộp change mới vào commit vừa tạo.

a. Dùng amend

Tiếp tục sửa file, rồi:

git commit --amend --no-edit

b. Dùng reset rồi commit lại

git reset HEAD~1
# sửa file
git add .
git commit -m "commit"

Tình huống 6

Lỡ commit file phải nằm trong .gitignore

Ví dụ

.env, file db dump nặng…

a. Chưa push

Dùng reset HEAD~1 để khôi phục, discard file đó, thêm vào .gitignore, rồi commit lại.

git reset HEAD~1
# discard file nhạy cảm / bỏ stage
# thêm vào .gitignore
git add .
git commit -m "commit"

b. Đã push qua nhiều commit (cần bỏ lịch sử)

Quét và bóc sạch file .env ra khỏi toàn bộ commit cũ:

git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env" \
  --prune-empty --tag-name-filter cat -- --all

Sau đó thêm .env vào .gitignore và commit lại:

git add .
git commit -m "remove file .env from git"
git push origin main --force

Cẩn thậnpush --force ghi đè lịch sử trên remote. Chỉ dùng khi hiểu rõ và team đồng ý.

Tình huống 7

Quay lại commit cũ

Ví dụ

Ở commit A → làm sang commit B, đã push hết; lúc test lỗi nhiều, muốn về commit A làm lại.

a. Checkout commit rồi copy thủ công

git log --oneline
git checkout 4b6bd5d

Copy các file code, về lại branch cũ, paste vào rồi tiếp tục. Cách này thủ công và không phù hợp với git.

b. Dùng HEAD nếu biết lùi bao nhiêu commit

Ví dụ 4b6bd5d là commit thứ 3:

git reset HEAD~3

Sau đó sửa code, add, commit lại. Cách này vẫn lưu lịch sử trên web.

Cách chuẩn hơn (theo tut)

Reset cứng local về commit A, rồi force push:

git reset --hard 4b6bd5d

# nếu commit B là commit vừa tạo:
git reset --hard HEAD~1

git push origin main --force

Sau đó mới tiếp tục làm.

Hoặc dùng revert

git revert <ma_commit_B>

Sau đó tiếp tục làm rồi push sau.

Tình huống 8

MR bị conflict — không merge vào main được

Luồng trong tut: pull main → merge main vào branch → fix → đẩy commit mới.

  1. 1

    Pull main về

  2. 2

    Merge main vào branch của bạn

  3. 3

    Fix conflict

  4. 4

    Đẩy commit mới (lên branch, không phải main)

git checkout main
git pull origin main
git checkout ten_branch
git merge main

# sửa conflict
git add .
git commit -m "fix conflict"
git push origin ten_branch

Chú ýPush ten_branch, không phải main — vì đang fix conflict trên branch đó.

Tình huống 9

dev nhiều tính năng — chỉ merge một phần vào main

Tình huống

Repo có dev và main. dev có thêm nhiều tính năng nhưng chỉ được merge vào main một số (còn lại đợi khách duyệt).

Đầu tiên: tạo 1 branch mới từ main, checkout sang branch đó.

C1 — Cherry-pick

Xem tính năng đó ở commit nào, cherry-pick commit đó sang.

git cherry-pick <ma_commit>

C2 — Merge nhánh tính năng

Xem tính năng mới đó ở branch nào, merge branch đó sang.

git merge branch_tinh_nang

C3 — Làm thủ công

Tạo branch mới từ main, xem tính năng ở file nào, copy sang.

Tình huống 10

Sửa lại commit message vừa gõ

Ví dụ

Gõ sai chính tả trong message commit vừa tạo.

C1 — Reset rồi commit lại

Dùng HEAD~1 sau đó commit lại.

git reset HEAD~1
git add .
git commit -m "tên commit đúng"

C2 — Amend message

git commit --amend -m "tên commit mới"
